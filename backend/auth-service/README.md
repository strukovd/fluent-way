Проверил актуальный SQL схемы локально, без туннеля. **Перед коммитом есть одно обязательное исправление:** в [BaseEntity](/home/user/repository/pet/fluent-way/backend/auth-service/src/entities/common/base.entity.ts) поля `updated` и `removed` генерируются как `NOT NULL`, хотя при создании записи дат ещё нет. Для обоих поставь `nullable: true`; `default: null` не требуется. `created` уже правильно генерируется с `default now()`.

Твой вариант с `username` рабочий: сохранять только lowercase и оставить обычный `UNIQUE(username)`. Чтобы правило нельзя было обойти прямой записью в БД, позже можно добавить `CHECK (username = lower(username))` — **второй индекс для этого не нужен**. Несколько `NULL` в уникальном `username` PostgreSQL допускает, что подходит аккаунтам без логина. [Ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

Для блокировки не обязательно проверять БД на каждом запросе. Можно выдать короткий access JWT, например на 15 минут, а при обновлении проверять `isActive` в БД. Тогда блокировка вступит в силу не позднее истечения access JWT. С токеном на сутки задержка может составить почти сутки.

**Миграции рекомендую завести сразу**, особенно для постоянной БД на VPS: они сохраняют в Git точный SQL и порядок изменений. Не обязательно писать их вручную — MikroORM умеет генерировать заготовку, которую мы проверим перед применением. Прямой `schema:update --run` на VPS рискован: MikroORM предупреждает, что он может менять и удалять таблицы, включая неизвестные ему. [Миграции](https://mikro-orm.io/docs/migrations), [предупреждение о Schema Generator](https://mikro-orm.io/docs/schema-generator).
